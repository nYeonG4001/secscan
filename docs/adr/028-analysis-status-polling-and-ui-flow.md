# ADR-028: 분석 상태 폴링과 실행 화면 흐름

**Context**: 분석 요청은 즉시 `PENDING` 분석 이력을 만들고 백그라운드에서 실행된다. 사용자는 분석이 끝날 때까지 현재 상태와 다음 행동을 알아야 하며, E0 화면 설계는 상태 화면과 완료 뒤 결과 화면의 같은 분석 상세 경로를 이미 정의한다. 실시간 양방향 연결은 MVP 범위와 운영 복잡도에 비해 과하다.

**Decision**: 분석 생성에 성공하면 ADMIN은 `/projects/{projectId}/analyses/{analysisId}`로 이동한다. 해당 화면은 `PENDING`과 `RUNNING` 동안 3초 간격으로 `GET /api/analyses/{analysisId}`를 폴링하고, `COMPLETED`이면 같은 경로에서 결과 목록을, `FAILED`이면 실패 상태를 표시한다. 폴링은 완료, 실패, 화면 이탈 때 중단한다. WebSocket은 MVP에서 사용하지 않는다.

USER와 ADMIN 모두 권한 있는 분석의 상태를 조회한다. USER는 일반 실패 안내만 보며, ADMIN은 오류 코드, 상세 메시지, 제한된 실행 로그와 “현재 소스로 다시 분석” 행동을 본다. 상태 조회의 네트워크 또는 5xx 오류는 분석 실패로 바꾸지 않고 수동 새로고침 안내를 표시한다. 인증 401은 E2 공통 흐름대로 로그인으로 이동한다.

같은 프로젝트에 활성 분석이 있어 `409 ANALYSIS_ACTIVE`가 오면 응답의 `analysis_id`로 기존 분석 상태 화면에 이동한다. `409 SOURCE_UPLOAD_IN_PROGRESS`가 오면 화면 이동 없이 프로젝트 상세에 “소스 업로드가 진행 중입니다. 완료 후 다시 시도해 주세요.”를 표시한다. 소스가 없거나 활성 분석이 있으면 ADMIN의 분석 실행 버튼을 비활성화한다.

**Alternatives**: 요청이 끝날 때까지 대기, WebSocket 또는 Server-Sent Events, 고정 간격 폴링, 상태 폴링 없이 수동 새로고침

**Consequences**: 별도 실시간 인프라 없이 분석 상태를 최신으로 보여주며, 네트워크 오류와 분석 실패를 구분한다. 폴링 요청이 생기지만 단일 실행기와 교육용 MVP 규모에서는 3초 간격이 충분하다. 이후 실시간 알림이 필요하면 상태 API 계약을 유지한 채 전송 방식만 교체할 수 있다.

**References**: ADR-022, ADR-026, ADR-027, SFR-008, SFR-015, SEC-003, SEC-009
