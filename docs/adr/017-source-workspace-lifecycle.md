# ADR-017: 프로젝트 소스와 분석 스냅샷 작업영역 분리

## Context

같은 프로젝트에는 새 소스 업로드와 여러 분석 실행이 반복될 수 있다. 프로젝트의 현재 소스를 분석이 직접 사용하면 새 업로드가 과거 분석이 가리키는 코드와 줄 번호를 바꿔 결과 재현성이 사라진다. 반대로 모든 업로드 버전을 영구 보관하면 별도 버전 모델, 저장 용량 정책, 조회 화면이 필요해 MVP 범위를 넘는다.

ADR-006과 E1 데이터 모델은 분석 생성 시점의 소스 스냅샷을 보존하고, MVP 기간에는 자동 삭제하지 않기로 이미 정했다. E3에서는 이 결정을 실제 저장 흐름과 작업영역 분리 정책으로 구체화한다.

## Decision

- 서버가 관리하는 저장 루트 아래에 프로젝트 현재 소스, 분석별 스냅샷, 임시 검증 작업영역을 분리한다.

```text
storage/
  projects/{project_id}/source/       현재 등록된 소스
  analyses/{analysis_id}/source/      분석 시점 소스 스냅샷
  staging/{random_id}/                검증 중인 임시 압축 해제 위치
```

- 새 ZIP은 먼저 서버가 만든 무작위 `staging` 경로에 압축 해제하고, ADR-015와 ADR-016 검증을 모두 통과한 뒤에만 프로젝트의 현재 소스로 교체한다.
- 프로젝트 현재 소스의 교체는 성공한 새 소스만 보이도록 원자적으로 처리한다. 이전 현재 소스는 교체 성공 뒤 제거할 수 있다.
- 업로드 요청의 성공, 거부, 예외, 취소 경로는 `finally`에서 해당 `staging` 경로를 정리한다. 서버가 강제 종료돼 정리되지 못한 경로는 서버 시작 시 기본 24시간보다 오래된 `staging` 디렉터리를 정리한다. 이 보존 시간은 환경 설정으로 조정할 수 있다.
- E4에서 분석을 생성할 때 현재 프로젝트 소스를 분석 ID별 스냅샷 경로로 복사한다. 이후 프로젝트에 새 소스가 등록돼도 기존 분석 스냅샷은 바뀌지 않는다.
- 검증 실패, 제한 초과, 예외가 발생한 `staging` 경로는 항상 정리한다. 프로젝트 현재 소스와 분석 스냅샷은 이 정리 대상이 아니다.
- 분석 스냅샷은 MVP 동안 자동 삭제하지 않는다. 이 경로는 서버 내부에서만 사용하고 어떤 API 응답에도 노출하지 않는다.
- 사용자 입력 파일명이나 경로를 저장 경로로 사용하지 않는다. 프로젝트 ID, 분석 ID, 서버가 생성한 무작위 값만 사용한다.

## Considered alternatives

- 모든 프로젝트가 하나의 공용 업로드 폴더를 사용한다. 프로젝트 간 경로 충돌과 격리 실패 위험이 있어 선택하지 않는다.
- 프로젝트 현재 소스 하나만 보관하고 분석이 이를 직접 사용한다. 새 업로드 뒤 과거 분석의 근거와 재현성이 사라져 선택하지 않는다.
- 업로드마다 별도 버전을 영구 보관한다. 업로드 이력에는 유리하지만 버전 모델, 용량 관리, 조회 UI가 추가로 필요해 선택하지 않는다.
- 현재 프로젝트 소스와 분석별 스냅샷을 분리한다. 현재 소스 교체와 과거 분석 재현을 함께 지원하면서 MVP 데이터 모델과 일치해 선택한다.

## Consequences

- 분석마다 소스 복사본이 생기므로 저장 공간을 더 사용한다.
- 같은 소스의 중복 스냅샷을 해시로 공유하는 최적화는 참조 횟수와 삭제 정책이 필요하므로 MVP에서 하지 않는다.
- E3은 안전한 임시 작업영역과 프로젝트 현재 소스 교체를 구현한다. E4는 분석별 스냅샷 복사와 분석 실행을 구현한다.
- E3-08과 E4 테스트는 실패한 임시 경로가 남지 않고, 서버 시작 시 오래된 임시 경로가 정리되며, 새 업로드 뒤에도 과거 분석 스냅샷이 유지되는지 검증한다.

## MVP scope and deferred option

MVP에서는 프로젝트마다 최신 소스 하나만 관리하고, 분석마다 독립 스냅샷을 보존한다. 이 선택으로 과거 분석 결과의 코드 근거와 재현성은 유지하면서도 SourceVersion 데이터 모델, 버전 목록, 현재 버전 선택, 이전 버전 재분석, 버전 삭제와 저장 용량 관리 화면을 만들지 않아도 된다.

업로드마다 소스 버전을 보존하고 사용자가 분석 대상을 선택하는 방식은 사용자 편의 측면에서 유효한 후속 확장이다. 특히 이전 소스를 다시 분석하거나 코드 변경 전후를 비교해야 하는 운영 환경에서 가치가 크다. 다만 9일 MVP에서 이 기능을 구현하면 E1 데이터 모델 확장, API 계약, 권한 검증, 버전 UI, 저장 용량 정책과 테스트가 추가돼 업로드 보안과 실제 분석 실행에 쓸 시간이 줄어든다.

따라서 이 기능은 요구사항을 포기한 것이 아니라 후속 범위로 보류한다. 사용자가 과거 업로드 소스를 직접 선택해 재분석해야 하는 요구가 확인되거나, 소스 버전 비교가 필요한 운영 시점에 SourceVersion 모델과 버전 선택 UI를 별도 에픽으로 추가한다.
