# E1 데이터 모델 및 분석 계약 작업 상세

E1을 시작하면서 E1-01부터 E1-09까지 작업 템플릿을 채운다. 완료 조건과 테스트 경로는 구현 전에 고정하고, 실제 파일이 생기면 증거 열을 갱신한다.

## E1-01 사용자, 역할, 활성 상태 필드 확정

- 요구사항 매핑: SFR-001, SFR-003, DAR-002, SEC-001
- 결정 필요: 계정 식별자와 내부 인증 방식은 ADR-010 참조
- 완료 조건:
  - 사용자 데이터에 고유 식별자, 비밀번호 검증 정보, 역할, 활성 상태, 생성 시각, 수정 시각이 포함된다.
  - 비밀번호 원문이 모델, 스키마, API 응답에 포함되지 않는다.
  - ADMIN과 USER 역할 값이 모델과 응답에서 일관되게 사용된다.
- 결정 결과: 계정 식별자는 이메일 형식으로 사용한다.
- 테스트: 단위 테스트 `backend/tests/test_user_model.py`, 인증 응답 테스트 `backend/tests/test_auth_api.py`
- 증거: 테스트 실행 로그와 사용자 테이블 및 로그인 응답 확인

## E1-02 프로젝트 필드와 생성자 관계 확정

- 요구사항 매핑: SFR-004, DAR-003
- 결정 필요: MVP 소스 등록 방식과 위치값 의미는 ADR-006 참조
- 완료 조건:
  - 프로젝트에 명칭, 설명, 소스 유형, 분석 대상 언어, 소스 위치, 생성자, 생성 시각, 수정 시각이 포함된다.
  - 프로젝트 생성과 수정 API의 요청 및 응답 스키마가 같은 필드 정의를 사용한다.
  - 프로젝트 수정 시 생성자와 생성 시각이 변경되지 않는다.
- 결정 결과: 프로젝트 하나에 Java, JavaScript, Python을 복수 선택할 수 있다. `target_languages`는 허용된 언어 코드의 목록으로 저장한다.
- 결정 결과: 프로젝트 생성, 소스 업로드, 분석 실행을 분리한다. 프로젝트 생성 시 소스 위치를 입력하지 않으며, 업로드가 완료되면 시스템이 `source_type`과 `source_location`을 기록한다.
- 결정 결과: 프로젝트 설명은 선택 입력이다. 값이 없으면 화면에서 `설명 없음`으로 표시한다.
- 결정 결과: MVP에서는 프로젝트 삭제를 제공하지 않는다. 프로젝트는 등록, 조회, 수정만 지원한다.
- 구현 범위: 기존 스캐폴드에 있는 `DELETE /projects/{project_id}` 경로는 E1 구현에서 제거한다.
- 결정 결과: 프로젝트명은 화면에서 중복되지 않게 관리한다. 같은 이름을 등록하면 시스템이 `프로젝트명 (1)`, `프로젝트명 (2)`처럼 뒤 번호를 붙여 저장한다. 프로젝트 ID는 별도의 내부 식별자로 유지한다.
- 테스트: 모델 및 API 테스트 `backend/tests/test_project_api.py`
- 증거: 마이그레이션 실행 로그와 프로젝트 생성 및 수정 API 응답

## E1-03 프로젝트 접근권한 관계 확정

- 요구사항 매핑: SFR-005, SFR-006, DAR-004, DAR-010
- 결정 필요: 비인가 자원 응답 정책은 ADR-008 참조
- 완료 조건:
  - 프로젝트와 사용자의 접근 관계가 별도 테이블에 저장된다.
  - 같은 프로젝트와 사용자 조합의 중복 권한이 저장되지 않는다.
  - 접근 관계가 없는 사용자와 프로젝트를 조회할 수 있는 경로가 API 계약에 남지 않는다.
- 결정 결과: ADMIN은 모든 프로젝트를 조회하고 관리한다. USER만 `PROJECT_ACCESS`에 명시적으로 할당된 프로젝트를 조회할 수 있다.
- 결정 결과: USER는 권한이 부여된 프로젝트를 분석 이력 유무와 관계없이 즉시 조회할 수 있다. 분석 이력이 없으면 빈 상태를 표시한다.
- 결정 결과: USER는 권한이 부여된 프로젝트의 분석 상태와 결과를 조회할 수 있다. `FAILED` 상태에서는 일반 실패 안내만 표시하고 상세 오류와 실행 로그는 ADMIN에게만 노출한다.
- 결정 결과: USER의 프로젝트 접근권한을 해제해도 프로젝트와 분석 데이터는 삭제하지 않는다. 해당 USER의 목록에서는 즉시 숨기고, 직접 주소 접근은 404로 처리한다.
- 테스트: 관계 무결성 테스트 `backend/tests/test_project_access_model.py`
- 증거: 중복 권한 거부 테스트 로그와 데이터베이스 관계 확인

## E1-04 분석 실행 상태, 실행자, 시각, 오류 필드 확정

- 요구사항 매핑: SFR-015, DAR-005, DAR-008, DAR-009, SEC-009
- 결정 필요: 관리자와 일반 사용자의 오류 및 원본 정보 범위는 ADR-009 참조
- 완료 조건:
  - 분석 데이터에 프로젝트, 실행자, 분석 엔진 또는 방식, 분석 시점 언어 목록, 소스 스냅샷 위치, 상태, 생성 시각, 시작 시각, 완료 시각, 오류 정보, 실행 요약이 포함된다.
  - 허용 상태가 `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`로 통일된다.
  - 실행 요약은 구조화된 형식으로 저장된다.
- 결정 결과: 분석 상태는 `PENDING`, `RUNNING`, `COMPLETED`, `FAILED` 네 개만 사용한다. 시간 초과, 잘못된 파일, 분석 엔진 오류 같은 세부 원인은 `FAILED`의 오류 코드로 저장한다.
- 결정 결과: 프로젝트별로 `PENDING` 또는 `RUNNING` 상태의 분석은 하나만 허용한다. 진행 중인 분석이 있으면 새 분석을 생성하지 않고 현재 분석 상태를 안내한다.
- 결정 결과: 허용 상태 전환은 `PENDING → RUNNING`, `PENDING → FAILED`, `RUNNING → COMPLETED`, `RUNNING → FAILED`다. 완료와 실패 상태는 다시 진행 상태로 바꾸지 않으며, 재실행은 새 분석 이력을 생성한다.
- 결정 결과: 분석 생성 시 분석 엔진 또는 방식과 실제 적용할 언어 목록을 `ANALYSIS`에 복사해 보존한다. 이후 프로젝트의 분석 언어 설정이 바뀌어도 과거 분석 행은 변경하지 않는다.
- 결정 결과: 분석 생성 시 업로드 검증을 마친 프로젝트 소스를 별도 스냅샷 위치로 복사하고, 그 위치를 분석 행에 보존한다. 프로젝트 소스가 이후 바뀌어도 과거 분석의 스냅샷 위치는 변경하지 않는다. MVP 기간에는 이 스냅샷을 자동 삭제하지 않는다.
- 테스트: 모델 및 스키마 테스트 `backend/tests/test_analysis_schema.py`
- 증거: 스키마 검증 로그와 분석 응답 예시

## E1-05 진단 결과 공통 필드와 분석 시점 보존 필드 확정

- 요구사항 매핑: SFR-014, DAR-006, DAR-008, QLT-004
- 결정 필요: 진단 항목과 기준 식별자 스냅샷은 ADR-005, 조치 권고 스냅샷은 ADR-007 참조
- 완료 조건:
  - 진단 결과에 분석 실행, 진단 항목 식별자와 명칭, 분석 시점의 기준 식별자, 언어, 심각도, 신뢰도, 파일 위치, 메시지, 탐지 근거, 조치 권고, 원본 결과가 연결된다.
  - 카탈로그가 변경되어도 과거 진단 결과의 분석 시점 정보가 유지된다.
  - 미매핑 결과도 원본 결과와 함께 저장할 수 있다.
- 결정 결과: 권한 있는 사용자는 KISA 매핑 결과와 미매핑 결과를 같은 목록에서 조회한다. 목록은 전체, KISA 매핑됨, KISA 미매핑으로 필터링하며, 카탈로그 화면은 KISA 49개 항목만 표시한다.
- 결정 결과: KISA 매핑 여부는 `kisa_code`의 존재 여부로만 판단한다. API의 매핑 상태 필터값은 저장하지 않고 응답 또는 조회 조건에서 계산한다.
- 결정 결과: 결과 상세에는 권한 있는 사용자가 확인할 수 있는 취약 줄 주변 코드 일부를 제공한다. 관리자 소스 뷰어는 E1부터 E7까지 완료한 뒤 시간이 남을 때만 진행하는 선택 작업이며, MVP 완료 조건에는 포함하지 않는다.
- 테스트: 결과 스키마 테스트 `backend/tests/test_finding_schema.py`
- 증거: Finding 응답 JSON과 카탈로그 변경 전후 비교 로그

## E1-06 KISA 카탈로그 필드와 구현 상태 확정

- 요구사항 매핑: SFR-012, SFR-013, DAR-007, TST-006, QLT-002
- 결정 필요: 실제 탐지 우선순위와 미매핑 처리 방식은 ADR-011 참조
- 완료 조건:
  - 카탈로그에 식별자, 명칭, 설명, 기준 식별자, 분류, 항목 번호, 참조 정보, 활성 여부, 기본 심각도가 포함된다.
  - 49개 항목을 실제 탐지 구현 여부와 별개로 등록할 수 있다.
  - 구현 상태가 `지원`, `부분 지원`, `미지원` 중 하나로 표시된다.
- 결정 결과: ADMIN은 카탈로그 항목을 직접 등록하고 수정할 수 있다. USER는 카탈로그를 조회만 할 수 있다.
- 결정 결과: 카탈로그 항목은 MVP에서 삭제하지 않는다. 더 이상 사용하지 않는 항목은 `active` 값을 끄는 방식으로 비활성 처리한다.
- 테스트: 카탈로그 스키마 테스트 `backend/tests/test_catalog_schema.py`
- 증거: 카탈로그 항목 수 확인 로그와 목록 API 응답

## E1-07 API 요청 및 응답 스키마 작성

- 요구사항 매핑: SFR-002, SFR-004, SFR-005, SFR-008, SFR-014, SFR-016, SFR-017, SEC-003, SEC-004
- 결정 필요: 권한별 분석 응답 분리는 ADR-009, 비인가 응답은 ADR-008 참조
- 완료 조건:
  - `docs/api-contract.md`의 핵심 API마다 권한, 요청 필드, 응답 필드, 오류 응답이 정의된다.
  - 관리자와 일반 사용자 응답에서 노출 필드 차이가 명시된다.
  - `source_snapshot_location`은 어떤 역할의 API 응답에도 포함하지 않는다.
  - API 스키마가 엔티티를 직접 응답하지 않고 별도 응답 모델을 사용한다.
- 테스트: OpenAPI 스키마 확인 테스트 `backend/tests/test_api_contract.py`
- 증거: `/docs` OpenAPI 화면과 계약 테스트 실행 로그

## E1-08 Alembic 마이그레이션 작성

- 요구사항 매핑: DAR-001, DAR-003, DAR-004, DAR-005, DAR-006, DAR-007, DAR-010
- 결정 필요: 데이터베이스와 마이그레이션 기술 선택은 ADR-002 참조
- 완료 조건:
  - 빈 데이터베이스에서 `alembic upgrade head`가 성공한다.
  - 프로젝트, 분석, 진단 결과, 카탈로그 필드가 ERD와 일치한다.
  - 외래키와 중복 방지 제약이 마이그레이션에 포함된다.
- 테스트: 마이그레이션 통합 테스트 `backend/tests/test_migrations.py`
- 증거: 마이그레이션 실행 로그와 생성된 테이블 구조

## E1-09 모델, 스키마, API 계약 테스트 작성

- 요구사항 매핑: DAR-001, DAR-002, DAR-003, DAR-004, DAR-005, DAR-006, DAR-007, DAR-010, QLT-001, QLT-005
- 결정 필요: 별도 결정 없음. E1에서 확정한 모델과 API 계약을 검증한다.
- 완료 조건:
  - E1-01부터 E1-08의 필수 필드와 관계에 대한 테스트가 존재한다.

  - 마이그레이션 후 모델 조회와 API 응답 필드가 일치한다.
