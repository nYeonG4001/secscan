# Epic: KISA 기반 SAST 분석 플랫폼 MVP

## 목표

관리자가 Java, JavaScript, Python 소스코드를 등록하고 정적 보안 분석을 실행하면, 시스템이 분석 상태와 표준화된 진단 결과를 저장·조회할 수 있는 교육용 SAST 플랫폼을 완성한다.

이 에픽은 `docs/원본_요구사항목록.docx`를 기준으로 작성한다.

## 사용자 가치

- 관리자는 프로젝트별로 소스코드를 분석하고 분석 실행 상태를 확인할 수 있다.
- 권한 있는 사용자는 프로젝트의 분석 이력과 진단 결과를 조회할 수 있다.
- 학습자는 취약 코드, 탐지 근거, 수정 권고를 통해 보안약점의 원인과 대응을 확인할 수 있다.

## 범위

### 포함

1. 사용자 로그인 및 인증 수단 발급
2. 관리자/일반 사용자 역할 기반 접근 제어
3. 분석 프로젝트 등록·조회·수정
4. 프로젝트별 사용자 접근권한 부여·해제
5. Java·JavaScript·Python 소스 등록 및 관리. MVP에서는 파일 업로드를 지원하고, Git 저장소와 기관 내부 경로는 후속 범위로 둔다.
6. 프로젝트 단위 정적 보안 분석 실행
7. 소스 수집·언어 식별·코드 분석·진단 항목 실행·결과 정규화 흐름
8. 대기·진행·완료·실패 분석 상태 관리
9. 공통 형식의 진단 결과 저장 및 조회
10. 심각도 등 주요 속성 기반 진단 결과 필터링
11. KISA 개발보안 가이드 49개 항목 카탈로그 관리·조회
12. 작업영역 격리, 파일 경로 검증, 분석 자원 및 실행시간 제한
13. 인증·권한·분석·카탈로그·결과 관리 테스트

### 제외 또는 후순위

- 대시보드와 통계 시각화
- 분석 이력 비교 및 추이 분석
- PDF 보고서 내보내기
- 알림 기능
- 다국어 지원

## 하위 작업

현재 단계에서는 각 작업의 번호와 요구사항 매핑만 확정한다. 작업이 속한 에픽을 시작할 때 해당 작업에 결정 필요 항목, 완료 조건, 테스트, 증거를 추가한다. 요구사항 매핑의 기준은 `docs/requirements-matrix.md`다.

작업 상세를 작성할 때는 `docs/templates/epic-task.md`를 사용한다.

E1 작업 상세는 `docs/epic/e1-data-model.md`, E2 작업 상세는 `docs/epic/e2-auth-access-control.md`, E3 작업 상세는 `docs/epic/e3-upload-security.md`에 작성한다. E4부터 E7은 해당 에픽 착수 전까지 번호와 요구사항 매핑만 유지한다.

작업 번호:

1. E1-01 사용자, 역할, 활성 상태 필드 확정

4. E1-04 분석 실행 상태, 실행자, 시각, 오류 필드 확정

6. E1-06 KISA 카탈로그 필드와 구현 상태 확정
7. E1-07 API 요청 및 응답 스키마 작성
8. E1-08 Alembic 마이그레이션 작성
9. E1-09 모델, 스키마, API 계약 테스트 작성

- 사용자, 프로젝트, 분석 실행, 진단 결과, 진단 기준 필드 확정
- 분석 상태와 실패 정보 정의
- 공통 진단 결과 스키마 정의
- 프로젝트·분석·결과 간 관계 및 권한 규칙 정의

프론트/UI 작업:

- 프로젝트·분석·결과 용어와 필드명을 화면에서 일관되게 사용
- 로딩·빈 상태·오류 상태를 공통 컴포넌트로 정의
- API 결과에 없는 필드가 있을 때의 기본 표시 규칙 정의

완료 조건:

- 요구사항의 필수 데이터가 모델과 API 스키마에 표현된다.
- 프로젝트에 설명, 소스 유형, 분석 언어, 소스 위치, 생성자, 생성 시각, 수정 시각이 포함된다.
- 분석 결과에 진단 항목, 심각도, 신뢰도, 파일 위치, 메시지, 탐지 근거, 조치 권고, 원본 결과가 포함된다.
- 마이그레이션으로 새 스키마를 재현할 수 있다.

- 인증 토큰 발급·검증·만료 처리

- 프로젝트 소속 기반 분석·결과 접근 검증

- 비인가 프로젝트 자원은 404로 처리
- 일반 사용자와 관리자 분석 응답 필드 분리

프론트/UI 작업:

- 로그인 폼, 인증 실패, 만료된 토큰 상태 구현
- 관리자/일반 사용자별 메뉴와 액션 노출 제어
- 권한 없음 화면과 로그인 화면 리다이렉트 처리
- 프로젝트 접근권한 부여·해제 UI 구현

완료 조건:

- 인증되지 않은 보호 기능 요청이 차단된다.
- 일반 사용자가 프로젝트 생성, 권한 변경, 분석 실행을 할 수 없다.
- 권한 없는 프로젝트의 분석과 결과가 조회되지 않는다.
- 권한 없는 프로젝트, 분석, 결과 요청은 자원 존재 정보를 노출하지 않는다.
- 일반 사용자 응답에는 내부 오류와 원본 분석 로그가 포함되지 않는다.

6. E7-06 언어별 취약 코드와 정상 코드 샘플 작성
7. E7-07 외부 구성요소 취약점과 라이선스 점검
8. E7-08 프론트 핵심 흐름과 접근성 테스트
9. E7-09 요구사항별 실행 증거 수집

- 인증·권한 테스트
- 프로젝트 접근 통제 테스트

- 정상 샘플의 오탐 여부를 확인할 수 있다.

## 남은 결정이 필요한 항목

원본 요구사항은 특정 분석 엔진이나 실제 탐지 항목 수를 정하지 않는다. 구현 전에 다음을 결정해야 한다.

1. KISA 항목별 실제 탐지 우선순위와 지원 언어
2. Git 저장소 인증 방식과 기관 내부 경로 허용 범위
3. 분석 작업을 백그라운드 작업으로 처리하는 방식
4. SEC-010의 세부 검증 명령과 실행 증거

다음 항목은 결정 완료 상태다.

1. MVP 소스 등록은 파일 업로드이며, Git 저장소와 기관 내부 경로는 후속 범위다. `docs/adr/006-source-registration-scope.md`
2. 조치 권고는 KisaCatalog 기본값과 Finding 분석 시점 스냅샷으로 보존한다. `docs/adr/007-recommendation-source.md`
3. 프로젝트 자원 비인가 접근은 404, 인증 실패는 401, 관리자 기능 역할 부족은 403으로 처리한다. `docs/adr/008-unauthorized-response-policy.md`
4. 분석 응답은 일반 사용자용과 관리자용 스키마로 분리한다. `docs/adr/009-role-based-response-schema.md`

## 최종 완료 기준

관리자가 테스트 프로젝트의 Java, JavaScript, Python 소스코드를 업로드하고 분석을 실행할 수 있어야 한다. 분석은 상태와 오류 정보를 관리해야 하며, 완료 후 권한 있는 사용자는 표준화된 진단 결과를 목록·필터·상세 형태로 조회할 수 있어야 한다. KISA 49개 진단 기준은 카탈로그로 조회 가능해야 하고, 인증·권한·파일 처리·분석 실행 보안과 관련 테스트가 통과해야 한다.
