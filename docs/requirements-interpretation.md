# 요구사항 해석과 질문

## 기준

- 원본: `docs/원본_요구사항목록.docx`
- 원본의 요구사항이 다른 문서보다 우선한다.
- 원본만으로 결정할 수 없는 내용은 가정으로 표시하고 멘토 확인을 거친다.

## 현재 해석

### 확정에 가까운 내용

- 시스템은 Java, JavaScript, Python 소스코드의 정적 보안 분석을 지원한다.
- 관리자는 프로젝트를 관리하고 분석을 실행한다.
- 일반 사용자는 권한이 부여된 프로젝트의 분석 결과를 읽기 전용으로 조회한다.
- 분석 실행은 대기, 진행, 완료, 실패 상태를 가진다.
- 진단 결과는 공통 형식으로 저장하고 조회한다.
- KISA 49개 항목은 식별자, 분류, 항목 번호, 명칭, 설명, 구현 상태와 함께 관리한다.
- 프로젝트와 사용자, 분석 실행과 결과 사이의 관계 및 접근 권한을 검증한다.

### 멘토 답변 반영 내용

- 외부 정적 분석 도구를 연동해도 된다. 분석 엔진을 처음부터 직접 만들 필요는 없다.
- KISA 49개 항목은 모두 카탈로그로 관리하고, 실제 탐지는 기간 안에 가능한 많은 항목을 지원한다.
- MVP는 공식 KISA 49개 항목을 초기 시드로 등록한다. 관리자는 공통 등록 절차로 신규 진단 항목을 추가하고 기존 항목을 수정할 수 있으며, 중복 `kisa_code` 등록은 차단한다.
- 소스 등록은 파일 업로드, Git 저장소, 기관 내부 경로를 모두 지원하는 방향으로 설계한다.
- 계정 식별자는 이메일 형식으로 선택했다. MVP는 내부 계정과 비밀번호 방식으로 구현한다.
- 일반 사용자는 권한이 있는 프로젝트의 결과만 조회한다. 분석 오류 메시지와 실행 로그는 시스템 관리자만 조회한다.
- 일반 사용자는 권한이 있는 프로젝트의 분석 상태와 결과를 읽기 전용으로 조회한다. 분석 이력이 없으면 빈 상태를 표시한다.
- SEC-010은 구현과 테스트에서 별도 점검 항목으로 관리한다.
- SEC-010은 외부 솔루션과 오픈소스 구성요소의 취약점 관리, 라이선스 준수, 버전 관리, 보안 업데이트 방안을 요구한다.

## 멘토에게 확인한 질문

1. 정적 분석 엔진은 외부 도구를 연동해도 되는지, 아니면 분석 규칙이나 분석 엔진을 직접 구현해야 하는가?
2. KISA 49개 항목은 카탈로그로 관리하면 되는가, 실제 취약점 탐지도 49개 모두 구현해야 하는가? MVP의 최소 실제 탐지 범위는 얼마인가?
3. SFR-007의 소스 등록은 파일 업로드만 지원해도 되는가, Git 저장소나 기관 내부 경로 연동까지 필요한가?
4. SFR-001의 기관 계정은 내부 계정인가, SSO나 OAuth 같은 기관 인증 연동인가? 계정 식별자는 이메일, 사번 등 어떤 형식인가?
5. 일반 사용자는 권한 있는 프로젝트의 분석 상태와 결과만 보고, 상세 오류 메시지와 실행 로그는 관리자만 조회하면 되는가?

- 답변을 받으면 이 문서의 질문 상태와 답변을 갱신한다.

- SEC-010은 원본 문구에 맞는 구현 항목과 검증 증거를 별도로 연결한다.
